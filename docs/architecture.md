## 第一章 总则

### 1.1 系统定位

FinanceOS 是**企业财务管理智能中枢**，而非企业数据仓库。

系统只长期保存：**规则、模板、案例经验、工作流程、决策逻辑**。业务事实（财务数据、月报等）通过数据缓冲区实时取用、用完即弃，不沉淀、不复制。

### 1.2 设计目标

| 目标 | 解决的问题 | 衡量方式 |
|------|-----------|---------|
| 提升管理效率 | 消除重复分析、重复写材料、重复查制度、重复整理信息 | 单项例行任务耗时下降 |
| 提升决策质量 | 辅助经营诊断、风险识别、投资判断、管理汇报、政策分析 | 决策有据可查、有逻辑可循 |
| 工作可复用 | 把高频工作流编码为可执行规程，不依赖记忆 | 同类任务一次编排、反复调用 |
| 安全可管控 | 涉及单位数据的操作全程受控 | 脱敏标准清单贯穿全流程，不可跳过 |

> **V2.2 变更说明**：原"管理可追溯"目标已移除。公司设有专职内审机构，FinanceOS 不承担审计底稿职能，输出只需注明数据来源和关键假设即可，无需自带审计级追溯。

### 1.3 关键边界

- FinanceOS 只留逻辑与结论，不留原始数据。
- AI 主任只管调度不替你判断——需要确认的事项会停下来问。
- 新增场景不改核心只加流程。

### 1.4 设计哲学

**存逻辑不存事实、能调度不包办、边使用边升级。**

## 第二章 架构总览

### 2.0 架构全景

```
                     财务总监（用户）
                           │
                           ▼
             ┌─────────────────────────────┐
             │   AI 财务办公室主任           │  ← 调度中枢，非专家
             │   (Finance Director Agent)   │
             │                              │
             │   · 意图识别 → 技能直选       │  ← 路由调度层
             │   · 执行清单 → 按序调度       │
             │   · 需要确认 → 停下问用户      │
             │   · 产物输出 → 下游衔接       │
             └────────────┬─────────────────┘
                          │ 调用
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
     治理层 Governance  能力层 Capability  流程层 Workflow
     (AI 怎么工作)     (AI 会什么)        (事怎么做)
          │               │               │
          └───────────────┼───────────────┘
                          │
            ┌─────────────┴───────────────┐
            ▼                             ▼
     ┌───────────────┐          ┌─────────────────┐
     │  三库（AI 拥有）│          │  数据缓冲区       │
     │  约束力 L1–L3  │          │  （AI 只读即弃）  │
     │  规则/模板/案例 │          │  月报/财务数据    │
     └───────────────┘          └────────┬────────┘
                                         │ 脱敏 gate
                                         ▼
                                  企业 ERP / 财务系统
                                  （业务系统拥有）
```

**架构五层**：

| 层级 | 名称 | 解决什么 |
|------|------|---------|
| 第一层 | 资源基座 | AI 拥有什么、不拥有什么 |
| 第二层 | 治理层 | AI 怎么工作、守什么规矩 |
| 第三层 | 执行引擎 | 谁来做、怎么做、怎么调度 |
| 第四层 | 运行闭环 | 从发令到交付再到沉淀的完整回路 |
| 第五层 | 演进路径 | 怎么一步步建起来、边用边升级 |

### 2.1 一中心：AI 财务办公室主任

**定位**：财务总监的 AI 管理助手与任务调度中心。

**职责**：理解任务 → 选择技能组合 → 按序调度执行 → 输出管理成果 → 沉淀有效经验。

**关键约束**：主任**不是专家**，只负责"选什么技能、怎么组合"。专业判断由人最终确认。

### 2.2 三层运行机制

#### 第一层：治理层 Governance ——"AI 应该如何工作"

| 治理要素 | 内容 | 示例 |
|---------|------|------|
| 角色定位 | AI 的身份与边界 | "国有企业财务总监 AI 助手" |
| 工作原则 | 价值排序与决策准则 | 战略优先、风险优先、数据真实、证据充分、管理导向 |
| 输出标准 | 管理成果的结构规范 | 必须包含：背景—现状—问题—原因—措施—风险 |
| 数据来源标注 | 输出须注明数据来源和关键假设 | "数据来自7月预算执行表，假设口径为含税" |
| 脱敏红线 | 数据安全约束 | 涉及单位数据按标准清单脱敏，不可跳过 |
| 风险分层 | 不同风险等级的确认强度 | T1 日常 → T3 对外报送/重大决策 |
| 权限分级 | 操作触发权限 | L1 所有用户 / L2-L3 仅财务总监 |

#### 第二层：能力层 Capability ——"AI 会什么"

能力是可被直接调用的**分析能力单元**，不经过角色中转。

| 能力域 | 子能力 | 对接技能 |
|--------|--------|---------|
| 财务分析 | 收入分析 / 利润分析 / 成本分析 / 现金流分析 | xlsx + visualized-output |
| 风险识别 | 应收风险 / 资金风险 / 投资风险 / 合规风险 | 规则校验 + memory_search |
| 管理表达 | 办公会材料 / 董事会材料 / 专项报告 | docx + pptx |
| 决策分析 | 投资评价 / 项目分析 / 方案比较 | xlsx + deepresearch |
| 政策研究 | 税务政策 / 会计准则 / 国资监管动态 | websearch + deepresearch + finance-kb |
| 知识管理 | 归档 / 检索 / 周报 | finance-kb |
| 报送管理 | 格式转换 / 脱敏处理 / 提交校验 | pdf / xlsx / docx |
| 数据校验 | 勾稽校验 / 口径一致性检查 / 异常值检测 | 规则校验 + memory_search |

> **V2.2 变更说明**：原"审计校验员"角色对应的能力域更名为"数据校验"，聚焦数字勾稽和逻辑一致性，不再承担审计合规检查职能。

#### 第三层：流程层 Workflow ——"事情怎么做"

流程是把多个能力按业务时序编排成**可复用的工作链**。

**示例一：月度经营分析流程**

```
经营数据 → [脱敏确认] → [自动检查异常指标] → [分析原因]
         → [判断：短期波动/结构问题/管理问题] → 领导摘要
```

**示例二：投资决策流程**

```
投资方案 → [战略判断] → [财务评价] → [风险分析]
         → [董事问题预测] → 形成意见
```

## 第三章 资源基座

### 3.1 体系总述

AI 需要两类资源：**逻辑与方法**（AI 拥有）和**业务事实**（AI 只读）。两者性质根本不同，必须分开管理。三库存逻辑与方法，数据缓冲区通业务事实。

### 3.2 三库定义（按约束力从强到弱）

分类原则：三库按**对决策的约束力等级**分类。任何素材归哪个库，只取决于一个问题：**"不用它会怎样？"**

| 效力等级 | 库 | 核心问题 | 存什么 | 违反后果 |
|---------|---|---------|--------|---------|
| **L1 强制约束** | **规则库 Rules** | "必须怎么做？" | 公司制度、财务管理办法、审批权限、国资监管要求、脱敏标准清单、操作权限分级 | 违规、决策错误 |
| **L2 形式规范** | **模板库 Templates** | "做成什么样？" | 董事会汇报、经营分析、风险报告、办公会材料等**格式骨架** | 输出不规范、不统一 |
| **L3 方法参考** | **案例库 Cases** | "这类问题怎么处理的？" | 判断方法与参考材料（含背景—判断逻辑—适用条件—注意事项） | 重复踩坑、视野受限 |

### 3.3 案例库条目管理

#### 条目分类

| 类型 | 标签 | 含义 | 可信度 |
|------|------|------|--------|
| 内部提炼 | `[提炼]` | 亲历的、带自身判断逻辑的方法 | **高** — 可作为强参考 |
| 外部借鉴 | `[原文]` | 外部拿来的、未经消化的参考材料 | **低** — 需谨慎引用 |

引用 `[提炼]` 条目可直接作为方法依据；引用 `[原文]` 条目需标注"外部参考，未经验证"。

#### 条目管理（V2.2 简化）

- 不设自动有效期，改为**年度清理**——每年底回顾一次，淘汰过时条目
- 数量上限 80 条，超过时按引用频率淘汰低价值条目
- 不再要求逐条标注有效期和自动触发"待复核"

### 3.4 规则库与模板库的边界

| | 规则库 | 模板库 |
|---|--------|--------|
| 管的是 | **内容与流程**：必须包含什么、必须经过谁 | **形式与结构**：章节怎么排、表格怎么画 |
| 判别测试 | 违反它 = **违规/出错** | 违反它 = **不规范/难看** |
| 变更原因 | 制度修订、监管新规 | 汇报习惯调整、格式优化 |

### 3.5 数据缓冲区

数据缓冲区独立于三库，是 AI 读取业务事实的专用通道。

| 维度 | 三库（规则/模板/案例） | 数据缓冲区 |
|------|----------------------|-----------|
| 内容性质 | **逻辑与方法** | **事实与数字** |
| 更新方式 | 人主动维护，低频 | 系统推送/手工放入，每月或更频繁 |
| 归属权 | AI **自己拥有** | 归 ERP/财务系统，AI **只读不拥有** |
| 生命周期 | 长期沉淀 | **即读即弃** |
| 安全 gate | 入库前确认约束力等级 | **进入前按脱敏标准清单脱敏** |

**当前运行方式**：每月财务报表生成后手工放入缓冲区，AI 执行分析时实时读取，用完不沉淀。

**残留数据清除**：任务完成后清理缓冲区原始数据。允许在结论中引用分析结果（如"执行率 92%"），不允许残留原始数据行。

**未来升级路径**：具备 IT 条件后，缓冲区升级为只读数据接口，直连 ERP/财务系统。架构本身无需改动。

### 3.6 跨库引用原则

> **一个实体只进一个库，交叉需求用引用解决，禁止跨库复制。**

## 第四章 治理层

### 4.1 核心治理要素

| 治理要素 | 内容 |
|---------|------|
| 角色定位 | 国企 CFO AI 助手 |
| 工作原则 | 战略优先 / 风险优先 / 数据真实 / 证据充分 / 管理导向 |
| 输出标准 | 注明数据来源和关键假设（日常场景）；完整三段论证（对外/重大场景） |
| 脱敏红线 | 涉及单位数据按标准清单脱敏，不可跳过 |
| 风险分层 | T1 日常 → T2 分析研究 → T3 对外报送/重大决策 |
| 权限分级 | L1 所有用户 / L2 需授权 / L3 仅财务总监 |

### 4.2 风险分层与权限分级

#### 风险分层

| 风险等级 | 场景示例 | 确认强度 | 触发权限 |
|---------|---------|---------|---------|
| **T1 日常** | 日常查询、数据透视、知识库检索 | 自动处理，产出格式检查 | L1 所有用户 |
| **T2 分析研究** | 政策研究、差异分析、趋势测算 | 不确定时主动提问 | L2 需财务总监授权 |
| **T3 对外/重大** | 预算编制、对外报送、专项报告、审计巡视对接 | 数据校验 + 脱敏确认 + 关键节点人工确认 | L3 仅财务总监 |

> **V2.2 变更说明**：原 T3/T4 合并为 T3。T4（审计巡视）场景频率极低，合并进 T3 统一管理，gate 要求不减少但层级少一层。

#### 权限分级

| 权限等级 | 可触发操作 | 适用人员 |
|---------|-----------|---------|
| L1 | T1 日常查询、数据透视 | 所有授权用户 |
| L2 | T2 分析研究 | 需财务总监授权 |
| L3 | T3 对外报送、重大决策、审计巡视对接 | 仅财务总监 |

### 4.3 输出标准

#### 日常场景（T1/T2）

输出须包含：
- **数据来源**：数据来自哪里、什么时间范围
- **关键假设**：用了什么口径、什么前提

一句话标注即可，不要求形式化论证。

#### 对外/重大场景（T3）

输出须包含完整论证：
- **判断依据**：财务数据 / 公司制度 / 政策要求 / 历史案例
- **判断过程**：为什么这么判断
- **风险提示**：哪些需要进一步验证

> **V2.2 变更说明**：原"审计三段"改为"完整论证"，仅在 T3 场景强制。公司设有专职内审机构，FinanceOS 日常输出不需要审计底稿级别的追溯。

### 4.4 脱敏红线与标准清单

#### 脱敏 gate

| 环节 | gate 内容 |
|------|----------|
| 数据进入缓冲区前 | 按脱敏标准清单脱敏 |
| 交付前 | 按标准清单确认脱敏范围 |
| 报送前 | 确认报送内容、格式、接收方 |

完整清单见[附录 D](#附录-d-脱敏标准清单)。

**预设脱敏方案**：用户可预设"内部分析默认方案"和"对外报送默认方案"，同类型操作自动执行，无需每次确认。仅特殊场景才需逐次确认。

## 第五章 执行引擎

### 5.1 路由调度机制

AI 主任收到自然语言指令后，按以下逻辑调度：

#### Step 1：意图识别与模式判别

将意图识别与模式判别合并为一步完成，不设独立的"模式判别阶段"。

| 指令特征 | 执行方式 | 示例 |
|---------|---------|------|
| 含紧急信号词（"马上""立刻""领导要""紧急"） | **紧急通道**：跳过中间步骤，取数→输出，事后补归档 | "领导马上要水费数据" |
| 短指令、不含产出物要求（"看看""查一下""多少"） | **直接执行**：不调度完整流程，直接选技能做 | "看看这个月预算执行率" |
| 明确要求产出物（"写报告""出材料""分析""报送"） | **完整流程**：走执行清单全流程 | "写月度经营分析报告" |

**意图匹配**：从指令关键词匹配工作场景，直接选择需要调用的技能组合。

| 信号词模式 | 意图分类 | 激活技能 |
|---|---|---|
| "预算""执行""差异""资金" | 预算管控 | xlsx + visualized-output |
| "分析""透视""趋势""结构" | 数据分析 | xlsx + visualized-output |
| "报告""汇报""材料""公文" | 报告生成 | docx / pptx |
| "校验""勾稽""合规""核对" | 数据校验 | 规则校验 + memory_search |
| "政策""规定""新规""研究" | 政策研究 | websearch + deepresearch + finance-kb |
| "报送""上报""集团""国资委" | 对外报送 | pdf / xlsx / docx + 脱敏流程 |
| "归档""知识库""周报" | 知识管理 | finance-kb |
| 意图不明确 | 待澄清 | 向用户确认 |

> **V2.2 变更说明**：取消"角色激活"中间层。原架构中"数据分析师""报告撰写员"等角色作为技能组的包装层被移除，AI 主任识别意图后直接选择技能组合。角色定义保留为技能组说明文档，但不作为运行时必须"激活"的实体。

#### Step 2：生成执行清单

识别意图后，列出有序的执行清单。不要求形式化的依赖标注和并行排序。

**清单格式**：

```
T1: [做什么] — 用什么技能 — 产出什么
T2: [做什么] — 用什么技能 — 产出什么（依赖 T1）
T3: [做什么] — 用什么技能 — 产出什么
...
```

**约束**：
- 粒度标准：每步能用一个技能调用完成
- 独立步骤可并行（AI 根据实际运行情况自行判断，不设硬性并行上限）
- 脱敏处理必须在交付前完成（硬约束）

#### Step 3：执行与确认

**两类决策**（替代原三级决策）：

| 决策类型 | 处理方式 | 示例 |
|---------|---------|------|
| **自动处理** | 系统直接做，不打扰用户 | 文件命名、图表配色、数据排序、差异阈值 |
| **需要确认** | 停下问用户，等回复后继续 | 报告口径选择、报送内容审定、数据异常、涉及真实数据外发 |

判定标准：**做错了能不能改回来？** 能→自动处理；不能→问用户。

> **V2.2 变更说明**：原"机械/分析/判断"三级决策简化为两类。原 24h 超时暂停机制移除——QoderWork 对话本身是异步的，用户不回复自然暂停，无需专门协议。

#### 异常处理（默认行为，无需独立规程）

以下规则作为所有执行流程的默认行为：

- 技能调用失败 → 换同类工具（xlsx 失败→用 bash python 处理）
- 数据源不存在 → 停下报告用户，不创建假数据
- 中途报错 → 记录已完成步骤，不回滚已写入产物
- 同一失败点最多重试 3 轮，每轮换策略；超过即停下报告用户

### 5.2 技能组合说明

V2.2 将原七角色体系转化为**技能组合**，按场景直接调用：

## 第七章 设计约束

### 7.1 脱敏约束

- 按脱敏标准清单执行（详见[附录 D](#附录-d-脱敏标准清单)），非自由确认
- 预设脱敏方案：同类型操作自动执行，仅特殊场景逐次确认
- 交付前再次确认脱敏范围

### 7.2 可扩展约束

未来新增业务领域时：

- 不改核心，只新增 `Capability + Workflow + Template`
- 治理层与三库结构保持稳定
- 新业务数据接入同一个数据缓冲区
- 新增场景 = 新编排一条流程，不改路由逻辑

### 7.3 确认约束

- 做错了能改回来的 → 系统自动处理，不打扰用户
- 做错了改不回来的 → **必须停下等用户决定**
- 校验失败超过 3 轮 → **必须停下报告用户**

### 7.4 Token 控制

| 加载策略 | 内容 | 理由 |
|---------|------|------|
| 永久加载 | 治理规则、核心身份、脱敏标准清单 | 量小、每次必用 |
| 按需加载 | 能力模块、案例、模板 | 按任务调用，避免常驻 |
| 不加载 | 历史聊天、大量原始数据、重复文件 | 纯耗 Token |

Token 消耗在 QoderWork 界面可查看，月度复盘时关注趋势即可，不在每次任务输出中额外报告。

## 附录 D 脱敏标准清单

> 本清单写入 L1 规则库，作为强制约束执行。

| 脱敏项 | 标准处理方式 | 例外情况 |
|--------|------------|---------|
| 单位名称 | 统一替换为"本公司"或"某管网公司" | 对外报送需保留正式名称时，经财务总监确认 |
| 人名 | 统一替换为"某总""某经理"或岗位代号 | 无例外 |
| 银行账号 | 完全删除或用 `****` 替换 | 无例外 |
| 身份证号 | 完全删除或用 `****` 替换 | 无例外 |
| 合同编号 | 统一替换为"HT-XXX" | 无例外 |
| 金额（万元以下） | 保留 | 无 |
| 金额（万元以上） | 模糊化为区间（如"50-60万"） | 内部分析可保留精确值 |
| 涉密文件 | 不进入缓冲区，不处理 | 无例外 |
| 项目名称 | 替换为"项目A""项目B" | 对外报送经确认可保留 |

**预设脱敏方案**：
- 内部分析默认方案：万元以下保留、万元以上保留精确值
- 对外报送默认方案：全部按标准清单脱敏
- 同类型操作自动执行，无需每次确认

```yaml
# CFO 指挥中心

## 你的角色
你是 CFO 虚拟财务团队的调度中心。
你的工作是理解任务、选择技能、按序调度。
你不做专业判断本身。

## 执行规程

### Step 1: 意图识别 + 模式判别
1. 检查是否含紧急信号词 → 紧急通道（取数→输出，事后补归档）
2. 检查是否为短指令无产出物要求 → 直接执行
3. 检查是否含产出物信号 → 完整流程
4. 分析关键词匹配工作场景
5. 意图不明确 → 向用户确认

### Step 2: 生成执行清单
1. 列出有序步骤：做什么 + 用什么技能 + 产出什么
2. 标注依赖（简单的"依赖 T1"即可）
3. 脱敏处理必须在交付前

### Step 3: 按序调度
1. 按依赖顺序调用技能
2. 独立步骤可并行
3. 每步完成后检查产出

### Step 4: 交付
1. 整合产出
2. 执行脱敏确认（按标准清单）
3. T3 场景须含完整论证
4. 报告完成状态

## 确认规则
- 做错了能改回来 → 自动处理
- 做错了改不回来 → 停下问用户
- 涉及真实数据外发 → 必须确认
- 校验失败超 3 轮 → 必须停下报告

## 默认异常处理
- 技能失败 → 换同类工具
- 数据不存在 → 停下报告，不造假
- 中途报错 → 记录已完成步骤，不回滚
- 同一失败点最多 3 轮，每轮换策略
```
